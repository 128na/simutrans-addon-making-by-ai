# sve_analyzer 高速化検証：解凍処理のRust/JS比較

作業日: 2026-08-24

## 目標

`refs/sve_analyzer`（Vue2ブラウザアプリ、セーブデータ解析）の処理速度がボトルネックだった問題について、
Rust/Goでのデスクトップアプリ化で高速化できるか検証する。

当初は`refs/save`のセーブデータをXML形式とみなしてsax相当のXMLパース速度を比較する予定だったが、
実際のファイルは全てSimutrans独自のバイナリ形式（gzip/bzip2圧縮）だった。バイナリ形式を
`refs/simutrans`（本家C++実装）に沿ってフルパースする場合、タイル情報(`planquadrat_t`/`grund_t`)が
持つオブジェクトリスト(`objlist_t`)が30種類以上のオブジェクト型を動的ディスパッチする可変長構造で、
かつ長さプレフィックスが無いため「読み飛ばす」だけでも各型のバイナリ仕様をバージョン分岐込みで
再実装する必要があり、多日〜数週間規模になることが判明。このため今回は**解凍処理（gzip/bzip2展開）
の速度比較のみ**にスコープを絞ってPoCを実施した。sve_analyzerはこの解凍もブラウザ内でJS実装
（`unbzip2-stream`、webpack経由でpure JSポリフィルされる`zlib`）で行っており、パース処理と並ぶ
ボトルネック候補である。

## 結果

達成（解凍処理単体でRustが約2.5倍高速という結果を実測）

## 試したこと

- `refs/save`配下の18個の実セーブデータ（168KB〜11MB、gzip16件・bzip2 2件）を対象に、
  同一ファイル・同一マシンでRust版とJS版の解凍時間を計測。
- Rust版（`rust/`）: `flate2`（pure Rustバックエンドのminiz_oxide）でgzip、`bzip2-rs`（pure Rust
  decoderのみ実装）でbzip2を展開。
- JS版（`js/`）: sve_analyzerが実際に依存している`unbzip2-stream`でbzip2を展開。gzipはNode.js組込みの
  `zlib`（内部はネイティブCライブラリ、ブラウザ実行環境とは条件が異なりフェアでない）と、
  ブラウザ向けpure JS実装である`pako`（`GZIP_IMPL=pako`環境変数で切替）の両方を計測し、
  ブラウザ実行に近い条件は`pako`版とした。
- 各ファイルについてディスク読み込み時間と展開処理時間を分離して計測（`process.hrtime.bigint()` /
  `std::time::Instant`）。

### 実行方法

```bash
# Rust版
cd try-out/sve_decompress_bench/rust
cargo build --release
./target/release/bench.exe

# JS版（pure JS実装での比較、ブラウザ実行に近い条件）
cd try-out/sve_decompress_bench/js
npm install
GZIP_IMPL=pako node bench.js
```

### 計測結果（2回計測して安定性を確認）

全18ファイル合計（生データ約63MB → 展開後約404MB）の解凍処理時間:

| 実装 | 1回目 | 2回目 |
|---|---|---|
| Rust (flate2 pure-Rust + bzip2-rs) | 1612.75ms | 1569.80ms |
| JS (pako pure-JS + unbzip2-stream) | 4004.09ms | 3941.73ms |

**約2.5倍の高速化**（pure実装同士のフェアな比較）。内訳では特にbzip2が顕著:

| 形式 | Rust | JS | 倍率 |
|---|---|---|---|
| gzip合計（16ファイル、pako比較） | 約514ms | 約1644ms | 約3.2倍 |
| bzip2（1ファイル、11MB→82MB） | 約1099ms | 約2319ms | 約2.1倍 |

参考: Node.js組込み`zlib`（ネイティブC、非フェア比較）だと gzip合計は約514ms（Rustとほぼ同等）——
ブラウザ内では使えない実装なので実際の高速化効果としては`pako`との比較が妥当。

## 得られた知見や失敗

- **検証対象データの前提確認が重要だった**: `refs/save`は当然XML形式だろうという思い込みで進めかけたが、
  実際は全てバイナリ形式だった。事前に`file`コマンド等でマジックバイトを確認すべきだった。
- **バイナリ形式の直接パースは非現実的な規模**: XML形式が自己記述的（タグで区切られ、未知の要素も
  読み飛ばせる）なのに対し、Simutransのバイナリ形式は長さプレフィックスの無い可変長オブジェクトリストで、
  型ディスパッチ(`obj_t`)により30種類以上のクラスの`rdwr()`をバージョン分岐込みで再実装しないと
  「読み飛ばす」ことすらできない。sve_analyzerがXML形式のみサポートしている（バイナリ非対応）のは
  合理的な設計判断だったと分かった。デスクトップアプリ化する場合も、セーブデータのXML書き出し
  （Simutrans側の設定）を前提にする方が現実的。
- **JS側の「本当の実行環境」に注意**: Node.jsの`zlib`はネイティブCバインディングなので、Node.js上での
  ベンチマークをそのまま「ブラウザでの速度」として扱うと不当にJSが有利に出る。webpackがブラウザ向けに
  `zlib`をpure JSポリフィル（実質`pako`相当）に差し替えることを踏まえ、`pako`で計測し直すことで
  フェアな比較になった。
- **解凍だけでもデスクトップアプリ化の価値はありそう**: 今回はXMLパース本体（sax相当）の比較は
  スコープ外にしたが、解凍処理だけで2.5倍の差が出ており、これはパイプライン全体（解凍→XML/バイナリ
  パース→UI描画）の一部に過ぎない。実際のsve_analyzerではXMLパース（sax、pure JS）も同様にネイティブ
  実装で高速化できる可能性が高く、Tauri（Rust）でVueフロントエンドを流用しつつパース部分だけ
  ネイティブ化する構成が引き続き有力な選択肢。次にXML形式のセーブデータを用意できれば、
  パース本体（`quick-xml`等）まで含めた比較を行いたい。
