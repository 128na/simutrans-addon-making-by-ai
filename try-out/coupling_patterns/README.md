# 車両連結パターン列挙 PoC

作業日: 2026-08-02

## 目標
vehicle dat の `constraint[prev][N]` / `constraint[next][N]` から、同梱車両で
組み立て可能な編成パターン（例: `A-B-C`, `A-C`）を列挙する機能を作れるか検証する。
最大の懸念点は連結がループするケースをどう扱うか:

- 中間車が自分自身を許容する（例: `A-B-B-...-B-C`）
- 2両が相互参照する（例: `A-C-A-C-...`）
- 単一車両が自己ループする（例: `A-A-...-A`）

これらはいずれも理論上「有効な編成が無限に存在する」ケースであり、単純な深さ優先探索
だけでは停止しない。

加えて実データでは以下2パターンも起こりうるため、途中から追加検証した:

- **制限なしの車両**（`constraint[next]`自体が無い）: このディレクトリ内の車両に
  限らず、ゲーム内のどの車両とも連結しうる
- **連結指定はあるが参照先車両がこのディレクトリに存在しない**（dangling reference）:
  相手側の`constraint[prev]`を確認できないため、実際に繋がるかどうか不明

## 結果
達成。公開されているpak128アドオン3種（下記）でも実際に動作を確認した。
`enumerate_patterns.py` として、以下の2段構えで実装した:

1. **ループ検出（Tarjanの強連結成分分解）**: サイズ>1のSCC、または自己ループを持つ
   車両を事前に検出し、「この車両グループは無限に編成パターンが存在する」と警告する。
2. **`--max-len` で打ち切った幅優先(BFS)列挙**: 両数の短い順に確定させていくことで、
   ループの有無に関わらず必ず停止し、かつ `--max-results` に達しても短い（自然な）
   編成が先に出揃う。`--max-results` で総件数の上限も設定できる（分岐が多い
   非循環グラフでの組合せ爆発対策。当初は深さ優先だったが、実データ検証中に
   「ループを周回した長い編成ばかりが上位を占めて短い編成が埋もれる」問題が見つかり
   BFSに変更した。詳細は下記「実データでの検証」参照）。

`refs/simutrans-dat-linter` の `dat_linter analyze --kind coupling`（実装は
`couplings.rs`）とは役割が異なる点に注意: あちらは「この車両を含む有限な編成が
1つでも組み立て可能か」という**充足可能性判定**のみで、実際のパターン列挙は行っていない。
本PoCはその一歩先（実際にパターンを表示する）を検証した。

「わからないもの」の表示も2種類用意した:

- **制限なしの車両**: `constraint[next]`自体が無い車両に到達したら、以降の相手を
  具体的に列挙せず `*` 1本で打ち切る（例: `A-B-*`）。ローカルの車両だけで具体列挙
  すると「これしか繋がらない」という誤った制限を暗示してしまうため
- **dangling参照**: `constraint[next]`が指す車両名がこのディレクトリに存在しない場合、
  `?` を付けて打ち切る（例: `A-D?`）。相手側の`constraint[prev]`が不明なので、
  本当に繋がるか・その先に続くかを判断できないことを明示する

## 試したこと

- **正規表現（状態遷移図からのMcNaughton–Yamada/Kleene流の状態除去法によるregex導出）
  も検討した**が、今回は見送った。制約グラフを「START/ENDを含むオートマトン」とみなし、
  中間ノードを1つずつ消去しながら遷移ラベルを結合・和集合・スター演算で合成していけば、
  `A-(B)*-C` や `A-(C-A)*-C` のような**有限の文字列でループを厳密に表現**できる。
  理論的には最も正確だが、PoCとしては実装・検証コストに対して「両数上限つき具体例列挙
  ＋ループ警告」で十分実用になったため見送った。将来「UIで正確な集合として表示したい」
  要求が出たら再検討する。
- `constraint[prev/next]`の読み取りは `refs/simutrans-dat-linter/src/couplings.rs` の
  `ConstraintSide`/`read_constraint_side` と同じ解釈（`none`は先頭/末尾を許す特別値、
  キー自体が無ければ無制約）を踏襲した独立実装にした。CLAUDE.md の方針
  （`refs/`配下のツールはこのリポジトリのコードから直接呼び出さない）に従い、
  dat_linterのRustコードをそのまま呼ぶのではなくPythonで最小限の再実装をした。
- `fixtures/` に4パターンの検証用ダミー車両（`no_loop`/`middle_repeat`/`two_cycle`/
  `self_loop_only`）を作り、それぞれ狙い通りの出力になることを確認した:

```
$ python enumerate_patterns.py fixtures/no_loop --max-len 5
2 件の編成パターン (--max-len=5):
  A-C
  A-B-C

  - B

  A-C
  A-B-C
  A-B-B-C

  A-C
  A-C-A-C

[警告] ... - A

  A

$ python enumerate_patterns.py fixtures/unconstrained --max-len 5

  - B
```

## 実データでの検証

公開アドオン3種（`refs/addons/`配下、gitignore対象の参照データ）で実行して確認した
（`--max-len 16`: 実在する車両モチーフの編成は最大でも16両程度という想定に合わせた）。

```
python enumerate_patterns.py "refs/addons/odakyu_70000/dat" --max-len 16 --max-results 30
python enumerate_patterns.py "refs/addons/shinkansen_tokai" --max-len 16 --max-results 30
python enumerate_patterns.py "refs/addons/mosa_E531/Source" --max-len 16 --max-results 30
```

- **`shinkansen_tokai`（東海道新幹線, 300/700/N700系）**: 警告ゼロ。全車両が
  `constraint[prev]`/`constraint[next]`を両側ともきちんと明示しており、SCCも
  無制約車両もdangling参照も検出されなかった。結果は実際の16両編成
  （`OBK_JRC_322(16)-...-OBK_JRC_323(1)`等）がそのまま列挙され、想定通り。
  きちんと制約を書き切った実データでは本ツールが素直に「短い警告なし」の出力になる
  ことを確認できた良い対照例。
- **`odakyu_70000/dat`（小田急の複数系列を1ディレクトリにまとめたアドオン集）**:
  187両という巨大な1グループがまるごとループ扱いされた。原因を実際に閉路を1本
  探して確認したところ、`odakyu1000_TcFront`（先頭車、`prev`未指定=無制約）と
  `odakyu1000_TcBack`（最後尾車、`next`未指定=無制約）のように、**「両端の車両は
  外側の制約を書かない」という一見自然な省略が、無制約同士の組み合わせによって
  「最後尾車の次に別系列の先頭車が来られる」という意図しないループを生む**ことが
  分かった。作者は物理的に「TcFrontは常に先頭、TcBackは常に最後尾」のつもりで
  書いていると思われるが、dat上はその意図を明示していない（`constraint[prev][0]=none`
  と書くのと「そもそも書かない」は、"先頭になれる"は同じでも"他の無制約車両の後に
  も来られてしまう"点で意味が異なる）。これは本ツールのバグではなく実データの
  仕様（またはdat設計の落とし穴）で、`*`表示と警告表示のおかげで初めて気づけた
  実例と言える。列挙結果自体は正しく、4両編成（`TcFront-M4-M5-TcBack`等）や
  6両編成が短い順にきちんと出てきた。
- **`mosa_E531/Source`（E531系）**: 1ファイル（`E531.dat`）に37件の`obj=vehicle`が
  `-`区切り行で連結されていた。当初のパーサは1ファイル1レコード前提だったため、
  同名キー（`name`や`constraint[...]`）が後続レコードで上書きされて壊れることが
  判明し、`refs/simutrans-dat-linter/src/parser.rs`の`parse_records`と同じ区切り
  ルール（行頭が`-`でレコード確定、重複キーは先勝ち）に合わせて修正した
  （`split_records`関数）。修正後は正しく37両を認識し、以下2つの実例が見つかった:
  - **dangling参照の実例**: `mosa_JRE_mohaE531-2000(3)`が`constraint[next]`で
    `mosa_JRE_kuhaE530-1000(10)`を参照しているが、この`Source`ディレクトリには
    存在しない（typoか、他ディレクトリに分割されているか、廃止された変種と推測）。
    `A-D?`表示が実データで実際に役立つケースを確認できた。
  - **意図的な中間反復車の実例**: `mosa_JRE_sahaE531-2000(2,6,7)`という車両名
    （10両編成の2・6・7号車のどこにでも挿入できる意図と読み取れる）が実際に
    自己ループを構成しており、SCC検出が正しく拾えていた。

これらの検証を通じて、**「深さ優先だと結果が長い周回パターンに埋もれる」問題を
実データで発見**し、上記の通りBFSへの変更に繋がった（`odakyu`と`mosa_E531`は
どちらもループを含むため、修正前は`--max-results`到達時に短い編成が1件も
含まれないことがあった）。

## 得られた知見や失敗

- **ループ検出（SCC）と列挙（BFS）を分離すると設計がシンプルになる**。
  列挙側は「両数上限があるので必ず停止する」という単純な性質だけで正しさを説明でき、
  ループの形（自己ループ/2両循環/N両循環）を個別に場合分けする必要がない。
  SCC検出は「無限に存在することをユーザーに事前に伝える」ための警告表示専用に割り切った。
- **`middle_repeat`のようなケースでは `A-C`（ループを1回も通らない編成）も
  正しく列挙される**点に注意。ループ中間車があっても「経由しない」編成は依然として
  有効な編成なので、警告を出しつつも通常の非循環パターンと同列に扱うのが正しい。
- **`two_cycle` の実際の car set 設計は難しい**: 単純に「AとCが互いを許す」だけだと
  A単独やC単独が先頭/末尾になれるかどうかで結果が大きく変わる。今回のfixtureは
  「Aは先頭になれるがCの後にも来られる／Cは末尾になれるがAの後にしか来られない」
  という非対称な制約にすることで、`A-C-A-C-...`という自然な交互パターンになるよう
  意図的に設計した。実際のpakset車両でこの手のfixtureを作る時は、`constraint[prev]`
  と`constraint[next]`が噛み合っているか（片方だけ許可していても逆側が拒否していれば
  エッジは成立しない）を両方確認する必要がある。
- **「制限なし」は必然的に自己ループでもある**: `constraint[prev]`も`constraint[next]`
  も無い車両は、`edge(x,x)`判定（両側とも無制約なら真）に引っかかるため、SCC検出の
  「自己ループ」警告にも同時にヒットする（`fixtures/unconstrained`のBが実例）。
  以前は「自己ループなら両数上限まで`B-B-B-...`と律儀に伸ばす」実装だったが、
  無制約車両は`current.next is None`の時点で`*`を出して即座に打ち切るよう変更した
  ことで、この種の無限自己ループも自然に1行へ収束するようになった（結果的に
  ループ対策の一般化にもなった）。
- **`*`と`?`はどちらも「この先は具体列挙しない」という明示的な打ち切り**であり、
  `--max-len`による打ち切りとは意味が違う。前者は「原理的にこのディレクトリの
  情報だけでは確定できない」ことを示し、後者は「情報はあるが両数上限で省略した」
  ことを示す。両者を同じ記号（例えば単なる省略記号）で表すと区別がつかなくなるため、
  別々の記号にした。
- **既存のdat_linterへの統合は保留**: `couplings.rs`の`check_satisfiability`と
  本PoCの列挙ロジックは相補的（前者はYes/No判定、後者は具体例提示）なので、
  将来的には`dat_linter analyze --kind coupling`に列挙サブモードとして統合する
  選択肢がある。ただし正規表現導出方式を採用するかどうかの判断が先に必要なため、
  今回はこのリポジトリ内の独立したtry-outスクリプトとして留めた。
